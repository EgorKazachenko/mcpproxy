# mcpproxy-deck

## Что это

Генератор презентаций по проекту **mcpproxy** — безопасный локальный MCP-прокси для
CLI-скриптов с Electron-контуром наблюдения.

Деки — **производные** от документации. `docs/` — источник истины, слайд — его проекция.
Если факта нет в `docs/`, его нет на слайде.

## Маршрутизация

| Запрос | Тип дека | Основные источники |
|---|---|---|
| «как это устроено», «архитектура» | `architecture` | `02-architecture.md`, `adr/` |
| «покажи сценарий S5», «разбери supply chain» | `scenario` | `08-demo-scenarios.md` + документы, на которые он ссылается |
| «чем мы лучше», «сравнение», «prior art» | `comparison` | `05-prior-art.md`, `04-research-findings.md` |
| «что мы покрываем», «OWASP», «карта атак» | `coverage` | `03-threat-model.md` |
| «честные выводы», «где мы небезопасны», «границы» | `honest` | `10-honest-limitations.md` |
| «метрики», «как меряем», «red team» | `metrics` | `09-metrics-and-eval.md` |
| «план», «эпики», «как делаем» | `roadmap` | `06-epics.md` |
| «подготовь демо», «полный дек» | `full` | всё, порядок из `08-demo-scenarios.md` |

Если тип не назван явно — спроси **один** вопрос через `AskUserQuestion` с вариантами
из таблицы. Не гадай: полный дек и разбор одного сценария — это разный объём работы.

## Гейт: сначала читаем, потом рисуем

**Это гейт, а не пожелание.** Перед написанием первой строки разметки:

1. **Прочитай `docs/README.md`** — карту документов.
2. **Прочитай каждый документ, указанный в таблице маршрутизации** для выбранного типа.
   Целиком, не по диагонали.
3. **Пройди по ссылкам.** Сценарии в `08-demo-scenarios.md` ссылаются на инварианты
   в `02-architecture.md`, ADR и атаки в `03-threat-model.md`. Слайд про сценарий
   без причины «почему это работает» — половина слайда.
4. **Загрузи скилл `artifact-design`** — калибровка объёма дизайна под задачу.
   Для дека с диаграммами дополнительно `artifact-diagramming`.

### Чего делать нельзя

- **Придумывать цифры.** Метрики в `09-metrics-and-eval.md` — это целевые значения
  и формат отчёта, а не измеренные результаты. Пока прогона не было, на слайде должно
  стоять «целевое» или прочерк, а не выдуманное число. Фальшивая метрика в презентации
  про безопасность убивает доверие ко всему деку.
- **Опускать оговорки.** У каждого сценария в `08-demo-scenarios.md` есть блок
  «Оговорка». Он попадает на слайд **всегда**. Демо без оговорок не вызывает доверия
  у технической аудитории — это зафиксированная позиция проекта, а не осторожность.
- **Улучшать формулировки в сторону силы.** «Мы поднимаем стоимость атаки» не превращается
  в «мы предотвращаем атаки». Если хочется усилить — значит, документ надо править,
  а не слайд.
- **Смешивать реализованное и запланированное.** Проект в стадии проектирования.
  Всё, что ещё не написано, помечается как план.

## Обязательные элементы любого дека

| Элемент | Правило |
|---|---|
| **Титул** | Одна фраза: что это. Не список фич |
| **Проблема до решения** | Первый содержательный слайд — всегда проблема, а не архитектура |
| **Две линии обороны** | Если дек длиннее трёх слайдов, различие «валидатор контролирует модель / песочница контролирует код» проговаривается явно. Это центральная мысль проекта |
| **Честные границы** | Последний слайд любого дека. Не опционально |
| **Источники** | Утверждения из разведки индустрии несут ссылку. Список — в конце `04-research-findings.md` |

## Тип: `architecture`

Порядок слайдов:

1. Проблема одной фразой + почему прямой Bash не годится
2. Топология: shim → daemon → UI (диаграмма из `references/diagrams.md`)
3. Почему Electron не хост MCP-сервера (ADR-0001)
4. **Две линии обороны** — центральный слайд
5. Инварианты И1–И8, по одному пункту на строку
6. Путь вызова: 13 стадий (sequence-диаграмма)
7. Модель прав песочницы: асимметрия чтения и записи + mandatory deny
8. Аудит: hash-chain
9. Принятые решения — таблица ADR с одной строкой обоснования каждый
10. Честные границы

## Тип: `scenario`

Один сценарий = 3–5 слайдов, по структуре из `08-demo-scenarios.md`:

1. **Что показываем** — постановка, что запускаем
2. **Что видит зал** — состояние UI, конкретные строки таймлайна
3. **Почему это работает** — механизм, а не лозунг
4. **За этим стоит** — инвариант / ADR / номер атаки / пункт OWASP
5. **Оговорка** — обязательно

Для `S5` (supply chain) — это кульминация демо, ей полагается развёрнутый слайд
с таблицей `none` vs `seatbelt`.

При запросе «дек по всем сценариям» держи ритм: S0–S4 по одному слайду, S5 — три,
S6–S10 по одному-два.

## Тип: `comparison`

1. Что уже существует: `tumf/mcp-shell-server`, `cfdude/mac-shell-mcp`, класс MCP-гейтвеев
2. **Что из этого правда** — первая половина нашего scope сделана. Не смягчать
3. Матрица возможностей из `05-prior-art.md`
4. Тезис: «allowlist защищает от того, что модель попросит запустить; он не защищает
   от того, что запущенный код сделает»
5. Что мы взяли готовым и не стали писать (srt, аннотации MCP, OTel, правила gitleaks)
6. Ответ на критерий фальсификации

Слайд 2 обязателен. Дек, который прячет существующие решения, разваливается от первого
вопроса из зала.

## Тип: `coverage`

1. Модель угроз: кому доверяем, кому нет. Ключевой сдвиг — **репозиторий недоверенный**
2. Карта атак A1–A15 с колонкой «чем ловим»
3. Подсветка шести классов, найденных в разведке (A5–A9, A11, A14) — они из спеки,
   CVE и OWASP, а не из фантазии автора
4. Таблица OWASP ASI01–ASI10 с покрытием ● ◐ ○
5. Честные границы

## Тип: `honest`

Полностью из `10-honest-limitations.md`, в его порядке: защищаем хорошо → частично →
не защищаем вообще → унаследованные слабости → формулировка для сцены → что считаем провалом.

Порог провала на слайде — **зафиксированный до прогона**. Это не самокритика,
а заявка на воспроизводимость.

## Тип: `full`

Порядок и тайминг — из таблицы в конце `08-demo-scenarios.md` (~7 минут).
Структура: проблема → что забрали у модели → happy path → первая линия →
**вторая линия (S5, кульминация)** → доверие → цифры → границы.

## Публикация

Дек — HTML-артефакт (`Artifact`), не файл в репозитории и не markdown в терминале.

- Один дек = один файл в `docs/decks/<type>[-<scenario>].html`
- Повторная публикация того же дека — тот же `file_path`, тот же URL
- `<title>` — короткое имя, не описание: «Архитектура mcpproxy», «Supply chain»
- Диаграммы — inline SVG или ```mermaid; никаких внешних CDN (CSP их режет)
- Тёмная и светлая тема обе обязаны читаться

Готовые исходники диаграмм — в `references/diagrams.md`, шаблоны слайдов —
в `references/deck-patterns.md`. Не перерисовывай архитектуру с нуля каждый раз:
топология и путь вызова канонические, они должны выглядеть одинаково во всех деках.

## Проверка перед выдачей

- [ ] Каждый факт на слайдах прослеживается до строки в `docs/`

- [ ] Все блоки «Оговорка» на месте
- [ ] Есть слайд «две линии обороны» (если дек длиннее трёх слайдов)

- [ ] Реализованное и запланированное визуально различимы
