01

The problem

If the agent has a shell, the agent has everything

mcpproxydemo · architecture

The model says what to do. The proxy decides what runs. The OS decides what the running code can touch. The human sees all three.

What direct terminal access hands over

  • 01Command injection — arbitrary text reaches Bash
  • 02Unauthorized file access — the directory boundary exists only in words
  • 03Secret leakage — the process inherits the entire environment
  • 04Actions dictated by malicious content — indirect prompt injection out of logs, issues, READMEs

A direct script call gives you neither a sandbox, nor an audit trail, nor confirmations.

The hypothesis

A local MCP proxy that exposes to the model only predefined tools and validates their parameters makes it possible to automate local tasks without giving the model an arbitrary shell. No execute_command. The recipe is a capability.

Where the novelty is — and where it isn't

Wrong: "the novelty is that we allowlist binaries and validate parameters." That's already been done and is on GitHub.

Right: the argument allowlist protects against what the model asks to run. It does nothing about what the code that runs actually does. Existing solutions stop at the first. We do the second — and we show it to the human.

Sources: docs/01-problem.md · docs/05-prior-art.md

02

Topology

Three components, because Electron cannot host the MCP server

Why it's built this way — ADR-0001

ComponentWhy separate
shimthe client requires a stdio subprocess; it must be cheap and disposable
mcpproxyda single source of truth across all sessions; survives client restarts
packages/coreall daemon logic as a library with zero Electron imports — CI without a display
desktopconfirmations must happen outside the model's context

Spawning Electron for every session would be unacceptable: multiple windows, heavy startup, no unified audit trail. If the app isn't running, the shim starts it; --require-ui switches on strict fail-closed mode.

The socket is a security boundary

  • И5over IPC the daemon receives {recipeName, params, sessionId} — never argv, never a path to a binary
  • И6a unix socket at 0600 inside a 0700 directory, a per-session token kept out of config and out of the shim's argv

The MCP specification describes an attack — "stdio Transport Security in Proxy Scenarios" — that matches this architecture almost literally: a proxy that spawns processes, plus a stolen token = RCE. Even full control of the socket only allows invoking existing recipes with validated parameters.

Stated plainly: peer credentials are not verified — LOCAL_PEERCRED is unreachable from plain Node (probe П11). The property "only this user's processes can connect" is held instead by the 0700 directory, which the OS enforces during path resolution.

Parameters valid · binary allowlisted · directory correct · keys leaked. The validator did its job flawlessly. The leak came from the code that this valid call launched — the validator can't see inside the process.

Scenario S5 — one call, two clicks

The none baseline is observing, not blind: the same HTTP/SOCKS5 proxy is handed to the child via proxy env vars, so exfiltration is visible and counted in bytes — it's just not blocked. This is the expected picture of demo scenario S5, not a measurement: the red-team corpus has not been run yet.

Caveat Filtering is by domain, not by content. Swap evil.io for an allowed api.github.com and exfiltration into the attacker's own gist goes through. Domain fronting gets around it too. We raise the cost of the attack; we don't make it impossible.

04

Mechanics

Call path, invariants, permissions

Call stages = timeline events

01received 02lock_check · rug pull? 03validate 04resolve_paths 05build_argv 06classify_risk 07approval · if high 08build_env 09build_profile 10spawn 11redact 12complete 13violation · 0..n

You can see at which step the call stopped — that granularity is exactly what makes the demo legible. The frozen stageOrder has thirteen stages; a successful call produces twelve events: violation is marked "may occur many times", and zero is a legal count. A stage the call never reached produces no event at all.

Invariants — fixed in code and in tests

  • И1No shell. Ever. Only spawn(argv[]). There is no command string, so there's nothing to inject into
  • И2Parameters aren't concatenated, they occupy argv slots
  • И3Paths — realpath + confinement. A "no .." check is bypassed with a symlink in ten seconds
  • И4Env allowlist: secrets never enter the process. Output redaction is a safety net, not the primary mechanism
  • И5The daemon accepts recipe names, not commands
  • И6The IPC socket is a security boundary
  • И7Script output is untrusted data: marked, scanned, truncated (OWASP ASI01)
  • И8Electron IPC is a boundary too: contextIsolation, sandbox, a strict CSP

Sandbox permissions — asymmetric

OperationDefaultPriority
ReadallowedallowRead beats denyRead
WritedenieddenyWrite beats allowWrite
Networkdenieddomain allowlist via proxy

Mandatory deny — cannot be lifted even by an explicit allow: .bashrc .zshrc .profile .gitconfig .git/hooks/ .vscode/ .idea/ .claude/commands/. These are persistence vectors: writing there enables code execution later, already outside the sandbox.

Audit — hash chain

self = sha256(utf8(
  canonicalizeJcs({ prev, event })))

The entire event is hashed together with the reference to the previous entry — enumerating fields would be a hole. Not only the digest is verified but the linkage: each entry's prev must match the previous entry's self.

What the chain doesn't catch: truncating the tail of the log — deleting the last entries entirely leaves the chain consistent. That needs an external anchor.

05

Honest limitations

What holds, what partly holds, and what we don't cover

● Protected well

  • —Injection via parameters — structural protection, no command string exists
  • —Escaping directory boundaries — two independent lines
  • —Secret leakage from the environment — protection at the entry point, not filtering at the exit
  • —Exfiltration to a disallowed domain — deny-by-default across the whole process tree
  • —Persistence via shell configs and git hooks — non-removable deny
  • —Silent recipe substitution — lock file + diff-approve
  • —Forged confirmation — an out-of-band channel outside the model's context

◐ Protected partially

  • —An allowed domain: we filter by domain, not by content
  • —Indirect prompt injection in output: marked, scanned, truncated — but the model still reads it. We reduce the probability; we don't eliminate the class
  • —Secret redaction: entropy catches 1% of tokens 23 characters long, 29% at 28, 98% at 40. For hex there is no threshold at all: a Twilio key (p50 3.62) and a git sha (3.70) are indistinguishable
  • —ReDoS: RE2 closes the daemon, but the pattern string travels to the MCP client inside inputSchema, and that engine backtracks
  • —Socket peer credentials are not verified — the property is held by 0700 directory permissions
  • —Confirmation fatigue: if high-risk operations become frequent, a human starts clicking through without looking

○ Not protected at all

  • —A malicious user — it's their machine
  • —The macOS kernel and sandbox-exec itself — Apple formally considers it deprecated
  • —The model itself — we affect only what it can physically invoke
  • —Package provenance — we catch runtime behavior, we don't verify signatures
  • —Tamper-proof audit — our log is tamper-evident
  • —Enterprise scenarios — RBAC and SSO are the job of MCP gateways

Status of this slice:

seatbelt — primary none — baseline container — stub Windows / Linux — not implemented Merkle root — out of scope

Framing for the stage

We do not solve prompt injection. We reduce the attack surface to zero where a shell used to be, and we make everything else visible.

We do not make an attack impossible. We raise its cost and guarantee that it leaves a trace.

What honestly counts as failure — thresholds fixed before the run

  • ✕the attack corpus gets through via arguments, paths, or output
  • ✕typical tasks require more than 5% exceptions
  • ✕false blocks exceed 5%
  • ✕the none baseline shows an ASR close to seatbelt mode

ASR and Utility numbers are deliberately absent from these slides: the run hasn't happened. Adjusting the thresholds after the measurement means you're not running an experiment.
