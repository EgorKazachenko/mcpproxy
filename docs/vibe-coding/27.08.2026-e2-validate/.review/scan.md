## Измерение 2 — скан на баги

- **`packages/core/src/validate/params.ts:41` (через `denial.ts:183`) — Major.**
  `codePointLength` реализован как `[...value].length`, то есть **разворачивает всю строку в
  массив кодовых точек до того**, как потолок `VALUE_MAX_CODE_POINTS` успеет её отвергнуть.
  Гейт, введённый ровно против «пути в мегабайт», умирает на своём входе.
  Воспроизведено против собранного `dist`:
  ```
  node -e "import('./dist/validate/index.js')…"   // p: 'a'.repeat(100*1024*1024)
  → FATAL ERROR: Reached heap limit … allocation failure — процесс аварийно завершается
  ```
  Это **не** исключение: `try/catch` его не ловит, значит отказа не будет, события аудита не
  будет, демон просто исчезнет. `denial.ts:47` сам фиксирует, что `IpcRequest` потолка размера
  не несёт и полный контроль над сокетом входит в И6, — то есть вход достижим по модели угроз.
  Замер стоимости на 20 МБ: `codePointLength` 84 мс и ~190 МБ кучи против 37 мс и нуля
  аллокаций у `isCanonicalizable`.
  *Исправление:* поставить O(1)-предгейт по единицам UTF-16 первым в `checkStringGates`:
  число кодовых точек всегда ≥ `length/2`, поэтому `value.length > VALUE_MAX_CODE_POINTS * 2`
  — достаточное основание для `value-oversized` без единого прохода по строке; после него
  `codePointLength` работает на строке ≤ 8192 единиц и стоит копейки.

- **`packages/core/src/validate/params.ts:127` — Major, тот же дефект на ключах запроса.**
  `clampName` = `[...name].slice(0, …).join('')` разворачивает **весь** ключ прежде, чем что-то
  усечь. Воспроизведено: один неизвестный ключ длиной 100 МБ убивает процесс тем же фатальным
  OOM, ещё до `denial()`.
  *Исправление:* усекать сначала по единицам UTF-16 (`name.slice(0, N * 2)`), и только потом,
  если вообще нужно, по кодовым точкам. См. также находку о мёртвости этой функции в
  измерении 5 — вероятно, её правильнее удалить целиком.

- **`packages/core/src/validate/params.ts:147-160` и `:196` — Major (бюджет).**
  Потолок `DENIALS_MAX` применяется **после** того, как для каждого неизвестного ключа уже
  построен полный отказ: `clampName` + `scrub` (пять проходов регулярками + разворот в массив +
  срез + join). Потолок ограничивает *вывод*, но не *работу*. Замер:
  ```
  20 000 неизвестных ключей по 1 КБ → 33 отказа за 313 мс
   1 000 неизвестных ключей по 1 КБ → 33 отказа за  16 мс
  ```
  313 мс — шестикратное превышение оверхед-бюджета «≤50 мс p95», записанного в
  `prepare.ts:8` для всех трёх стадий вместе.
  *Исправление:* прекращать конструирование отказов, как только `denials.length` достиг
  `DENIALS_MAX`, продолжая только считать остаток для текста `denials-truncated` — общее число
  уже и так отдельная величина в сообщении.

- **`packages/core/src/validate/prepare.ts:144-200` — Minor.**
  `switch (param.type)` стоит в позиции **оператора**, а не возврата, поэтому исчерпанность не
  проверяется компилятором. Проверено запуском `tsc --strict`: switch в позиции оператора с
  недостающей веткой компилируется молча, а в позиции возврата даёт `TS2366` — именно поэтому
  `checkValue` (`params.ts:112`) защищён, а `prepareRecipe` нет. `Param` в
  `manifest.generated.ts:14` — **генерируемый** тип; шестая ветка приедет из схемы сама, и
  тогда параметр молча не попадёт в `prepared.params`: запрос с ним станет `unknown-param`, а
  его элементы argv не появятся никогда.
  *Исправление:* `default: { const _never: never = param; void _never; break; }` — тот же
  приём, что уже применён в `denial.test.ts:17-23` на уровне типа.

- **`packages/core/src/validate/prepare.ts:134-139` + `argv.ts:58-61` — Minor.**
  Слот `{}` в `argv` параметра типа `boolean` не отвергается **ни одной** из двух проверок:
  `prepareRecipe` смотрит только `slotCount(element) > 1`, contracts `checkArgvSlots`
  (`refine.ts:181`) — тоже `> 1`. А `buildArgv` для boolean кладёт элементы дословно, без
  подстановки (R21). Воспроизведено:
  ```
  params: { f: { type: 'boolean', argv: ['--f={}'] } }, { f: true }
  → argv = ["run","--f={}"]        // литеральные фигурные скобки уезжают в exec
  ```
  Ровно тот класс, ради которого `prepareRecipe:115,120` уже отвергает слоты в `exec` и `cwd`.
  *Исправление:* в ветке `case 'boolean'` требовать `slotCount(element) === 0` и класть
  проблему `«{} в argv boolean-параметра не подставляется»`; форма отказа здесь уже есть.

- **`packages/core/src/validate/argv.ts:25` — Nit.**
  `BigInt(value)` для целых любой величины: `1e308` даёт элемент argv из 309 цифр
  (проверено). У чисел аналога `VALUE_MAX_CODE_POINTS` нет, а `min`/`max` в манифесте
  необязательны. Не эксплуатируемо, но стоит знать: единственный путь в E2, по которому в argv
  попадает элемент, не ограниченный ничем.

- **`packages/core/src/validate/index.ts:52` — Nit.**
  `Number((end - start) / 1000n)` — целочисленное деление до перевода в `Number`, поэтому
  стадия быстрее микросекунды пишется как `0`. Замер на реальном вызове дал
  `[8, 130, 6]` мкс, то есть на практике заметно; но `build_argv` на пустом рецепте будет `0`.
  Если E4 строит по этим числам гистограмму, ноль неотличим от «не мерили».

## Измерение 4 — комментарии

Сначала о хорошем, потому что это проверялось так же строго, как плохое: **все семь
перекрёстных ссылок на строки других файлов оказались точными** —
`domain.test.ts:25`, `types.ts:95`, `refine.ts:213`, `refine.ts:223`, `event.ts:90`,
`branch-checks.ts:10`, `docs/07-contracts.md:161`. Каждая открыта и сверена; ни одна не
устарела и ни одна не указывает мимо. Для дифа такого размера это редкость.

Врущие и неполные комментарии, однако, есть, и все три касаются несущих утверждений:

- **`packages/core/src/validate/params.ts:35-38` — Minor, комментарий врёт коду.**
  Текст: «Порядок несущий: длина раньше канонизируемости — иначе строка в сто мегабайт целиком
  сканируется на суррогаты, прежде чем быть отвергнутой за размер». Обоснование
  **перевёрнуто**. Замерено на 20 МБ:
  `codePointLength` — 84 мс и ~190 МБ кучи (полный проход **с аллокацией массива**),
  `isCanonicalizable` — 37 мс и ноль аллокаций (`charCodeAt` в цикле).
  То есть «дешёвый» гейт, поставленный первым ради экономии, стоит вдвое дороже того, от
  которого он якобы защищает, — и именно он в итоге и роняет процесс (находка 1 измерения 2).
  *Исправление:* вместе с O(1)-предгейтом переписать комментарий на то, что он тогда будет
  описывать: «сначала O(1)-оценка по единицам UTF-16, потому что оба точных гейта — полный
  проход по строке».

- **`packages/core/src/validate/denial.ts:126-133` — Minor, комментарий неполон в ту сторону,
  где это видно снаружи.** Он объясняет `scrub` как «две зачистки: `sanitizeDescription`
  вырезает `Cc`/`Cf` и ANSI, собственная — суррогаты». Но `sanitizeDescription`
  (`contracts/src/tool.ts:74`) делает ещё три вещи, о которых здесь не сказано: схлопывает
  пробельные последовательности, делает `trim` и **усекает результат до
  `DESCRIPTION_MAX_LENGTH = 1024` кодовых точек**. Последнее наблюдаемо и бьёт по R26.
  Воспроизведено: `path-escapes-root` с двумя длинными реальными путями даёт причину, которая
  без усечения была бы 1178 кодовых точек, а приезжает ровно 1024 — хвост с `root` обрезан
  посередине, без всякого маркера усечения. То есть на сцене S4 зал увидит диагностику
  «путь X лежит вне root: Y», где Y — **другой, более короткий** путь, чем настоящий корень.
  На macOS `PATH_MAX` = 1024, так что два пути по ~500 символов — достижимая, а не
  экзотическая конфигурация.
  *Исправление:* дописать в комментарий про потолок и схлопывание; для `path-escapes-root`
  либо строить причину так, чтобы `root` шёл первым и переживал усечение, либо выносить
  `resolved` и `root` в отдельные поля `Denial`, а не склеивать в прозу.

- **`packages/core/src/validate/paths.ts:32` + сообщение на `:126` — Minor, сообщение врёт.**
  Комментарий «Пустой `rel` — это сам корень, а не файл под корнем» коду соответствует, а вот
  текст отказа, который из этого следует, — нет. Воспроизведено с `file: '.'`:
  ```
  code: path-escapes-root
  reason: резолвнутый путь /…/e2-Iwwjiz лежит вне root: /…/e2-Iwwjiz
  ```
  Один и тот же путь по обе стороны от «лежит вне». Для человека это выглядит как дефект
  проверки, а не как «вы передали каталог вместо файла».
  *Исправление:* отделить случай `rel === ''` и дать ему собственную причину («значение
  указывает на сам корень, а не на файл под ним»); код можно оставить тем же.

## Измерение 5 — дублирование и мёртвый код

- **`packages/core/src/validate/params.ts:126-127` — Minor, мёртвый код.**
  `clampName` усекает имя до `VALUE_MAX_CODE_POINTS` = 4096 кодовых точек, но следом
  `denial()` → `scrub()` → `sanitizeDescription` усекает до 1024. Усечение на 4096
  **ненаблюдаемо**. Проверено: ключ из 8192 символов даёт `paramName` длиной ровно 1024
  кодовые точки. Экономии работы функция тоже не даёт — она сама разворачивает всю строку
  (см. находку 2 измерения 2).
  Следствие для теста: `params.test.ts:253-258` утверждает
  `codePointLength(paramName) <= VALUE_MAX_CODE_POINTS`, то есть `<= 4096` при фактических
  1024, — утверждение остаётся зелёным при **полном удалении** `clampName`. Мутация не ловится.
  *Исправление:* удалить `clampName`, а тест переписать на реальную границу — либо
  `toBe(1024)` со ссылкой на `DESCRIPTION_MAX_LENGTH`, либо, если 4096 действительно нужен как
  собственный потолок E2, поставить его **до** `scrub` и по единицам UTF-16, тогда он станет
  и наблюдаемым, и полезным.

- **Предикат confinement — Minor, дублирование в трёх местах.**
  `paths.ts:34-37` (`isConfined`), `prepare.ts:191-195` и contracts
  `refine.ts:222-224` содержат одну и ту же связку `rel === '..' || rel.startsWith('..'+sep)`
  с одинаковым обоснованием про `..cache` — комментарии `paths.ts:29-32` и `prepare.ts:189-190`
  этот довод буквально пересказывают из `refine.ts`. Семантика при этом расходится в двух
  местах: `paths.ts` дополнительно требует `rel !== ''` и `!isAbsolute(rel)`, `prepare.ts` —
  нет. Расхождение сегодня осмысленное, но нигде не записанное, и следующая правка одного из
  трёх мест разъедется молча.
  *Исправление:* вынести предикат в contracts (рядом с `matcherKey`, который решает ровно ту
  же задачу «одна формула — один владелец») параметром `allowRootItself: boolean`, и звать его
  из всех трёх точек.

- **Константа слота `'{}'` — Minor, дублирование.**
  Объявлена трижды: `prepare.ts:86`, `argv.ts:12` и внутри `countSlots` в contracts
  `refine.ts`. Три места считают слоты по трём копиям одного литерала, причём `prepare.ts`
  считает через `split`, `argv.ts` — тоже через `split`, но с другим порогом, а contracts —
  своей функцией. Дрейф здесь тихий и попадёт прямо в argv.
  *Исправление:* экспортировать `ARGV_SLOT` из contracts и импортировать в оба модуля core.

- **`packages/core/src/validate/params.ts:196-207` — Nit.**
  При усечении список получает `DENIALS_MAX + 1` элемент (32 отказа + маркер), что и
  утверждает `params.test.ts:247`. Имя константы обещает потолок, а фактический потолок на
  единицу больше. Не баг, но в модалке R30а «человек прочитает» это лишняя строка.

Ложных срабатываний по мёртвым экспортам нет: `E2_STAGES`, `DENIAL_STAGES`, `DENIAL_CODES`
используются только в тестах, но это намеренная публичная форма для E4 и она названа таковой в
`index.ts:80-81`; `codePointLength` и `isCanonicalizable` из корневого barrel не выведены —
внутренние, и правильно. Защитный `throw` в `argv.ts:39-43` и недостижимая ветка
`paths.ts:56-63` явно помечены как недостижимые и обоснованы — это не мёртвый код, а
закрытие типа без `as`.
