## Killed candidates (adversarial pass)

- **`packages/desktop/src/main/protocol.ts:77-90` (`handleAppScheme`) — `readFile` throwing after a successful `realpath` (TOCTOU race).** Not raised as a blocking finding: `protocol.handle`'s callback promise is owned and mapped to a network-error response by Electron itself, not by app code — this is the platform's outer handler, not a gap in this diff. Noted as VALID-NOT-BLOCKING only because it is genuinely unlogged, but demanding a log here is exactly "recurring environmental fact" territory (a file deleted mid-read), and Electron's own mapping already denies-by-default (404/network error), which is the correct security direction.
- **`resolveBundlePath` returning `null` for a path that escapes the bundle root (`protocol.ts:52-69`).** This is the literal "protocol request for a path outside the bundle" scenario named in the brief. Checked: it denies-by-default correctly (404) and requires the renderer to already be running attacker script under a strict `script-src 'self'` CSP to even attempt it — at that point the compromise is already total. VALID-NOT-BLOCKING: worth a record in a later run, not a blocker now, and adding a logging framework solely for this one path is not proportionate per the brief's explicit "do not demand a logging framework" instruction.
- **Missing `verifyChain` call at runtime in `packages/desktop/src/main/trace.ts`.** `@mcpproxy/contracts/audit` exports `verifyChain`/`ChainVerification` and the desktop package imports `ChainedEvent` from the same package but never calls `verifyChain` at runtime (only in `trace.test.ts`, to keep the committed fixture honest). This looked like exactly the "chain-hash mismatch" blind spot named in the brief. **Killed**: `docs/vibe-coding/27.08.2026-e7-ui/spec.md` (R14, and the "Отложено в ран 2" section) explicitly and deliberately defers `verifyChain`'s runtime wiring to run 2, together with its only consumer (the audit tab), with a written rationale: "без потребителя проверка цепочки в main была бы мёртвым кодом" (without a consumer, the check would be dead code in main). This is precisely the documented, owner-approved deferral the brief tells reviewers not to flag.
- **`cspModeFrom(nodeEnv)` on unset/unknown `NODE_ENV` (`csp.ts:10-12`).** Checked the standing "deny-on-error" lens explicitly. Falls to `'production'` (the strict policy) on anything other than the literal string `'development'`. This is already deny-on-error-correct; not a finding.
- **`sanitize`/`parseUiRequest` (`parse.ts`) on a malformed/prototype-polluting payload.** Returns `denied('bad-payload', ...)` with a specific, discriminating message per branch (speed not finite, speed out of range, unknown track, unknown command, unknown request kind) — this is exactly what question (e) asks for, not a finding.
- **`player.apply`'s `default`-less `switch` on `PlayerCommand.kind` (`player.ts:75-93`)** — the type is a closed union and `parsePlayerCommand` already rejects anything outside it before it reaches `apply`; no silent fallthrough is reachable.
- **`registerIpc`/`ipcMain.handle` being the only registration site (`ipc.ts:73-79`, `window.ts`'s four fixed `webPreferences` flags)** — these are structural invariants enforced by dedicated tests (`ipc.test.ts` per R6, `window.test.ts`), not error-handling gaps.

## Notes on scope

`packages/desktop/src` has zero `console.*` calls and no logging framework, confirmed by grep across the whole package — consistent with the brief. This review does not fault that absence in general; findings 1–3 above are cases where the *specific* failure path has no possible way to become visible at all (crash-before-window, dropped IPC rejection, dropped security denial), not cases where a generic "add logging" demand would apply.
