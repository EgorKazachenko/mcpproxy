# Порядок работ

Шпаргалка для себя. Обоснования — в [`docs/06-epics.md`](docs/06-epics.md).

## Правило номер один

**E0 делается в одиночку и до конца.** Пока `packages/contracts` не заморожен,
параллелить нечего: семь эпиков зависят от него. Соблазн «начну UI параллельно,
контракт по ходу допишу» стоит переписывания волны 1.

## Шаг 1 — E0, соло, без агентов

- [ ] Монорепо pnpm: `contracts`, `core`, `mcp-server`, `desktop`, `bench`
- [ ] JSON Schema манифеста (`07-contracts.md` → «Манифест рецептов»)
- [ ] Схема события — **OTel GenAI-совместимая**, 13 стадий
- [ ] MCP tool annotations в контракте, дефолты пессимистичные
- [x] Четыре рецепта-заглушки: `run_tests`, `build_project`, `analyze_logs`, `publish_release`
      (четвёртый — единственный high-risk, без него сценарию S8 нечего показывать)
- [ ] **Заморозка.** Дальше `contracts` меняется только явным решением

## Шаг 2 — волна 1, пять веток параллельно

Worktree на эпик, ветка `epic/E<N>-<slug>`. Пересечений по файлам быть не должно —
если возникло, значит E0 недоделан, возвращаемся.

| Ветка | Эпик | Трогает | Заметка |
|---|---|---|---|
| `epic/E1-policy` | Policy + lock | `core/policy` | lock-файл обязателен, не «потом» |
| `epic/E2-validate` | Валидатор + argv | `core/validate` | `string` без `pattern` = ошибка загрузки |
| `epic/E3-sandbox` | Песочница | `core/exec` | обёртка над `srt`, не свои SBPL |
| `epic/E6-audit` | Секреты + аудит | `core/audit` | правила из Secrets-Patterns-DB |
| `epic/E7-ui` | Electron | `desktop` | **на моках событий**, ядро не ждём |

E7 стартует вместе со всеми и идёт дольше — это нормально и правильно:
на демо UI важнее ядра.

## Шаг 3 — E4, соло

MCP-поверхность + shim + хардненинг IPC. Соло, потому что сшивает E1+E2+E3+E6
и здесь всплывут расхождения контракта.

- [ ] `tools/list` из манифеста с аннотациями
- [ ] Сокет 0600 + peer-cred check
- [ ] **Демон принимает только `{recipe, params}`** — никогда argv
- [ ] E2E: один рецепт проходит весь путь

## Шаг 4 — E5 и E8 параллельно

| Ветка | Эпик | Зависит |
|---|---|---|
| `epic/E5-approvals` | Двухканальные апрувы | E4 + E7 |
| `epic/E8-redteam` | Корпус + метрики | E4 e2e |

E8 — не тесты, а главный номер демо. Закладывать время как на фичу, не как на QA.

## Шаг 5 — E9, соло

Хардненинг (включая Electron-чеклист), демо-репо с вредоносной зависимостью,
прогон корпуса, репетиция по таймингу из `08-demo-scenarios.md`.

## Что никогда не параллелить

- E0 — шов
- E4 — точка сшивки
- Правки `packages/contracts` — только соло и с ревизией зависимых веток

## Расписки по правкам контракта

Здесь фиксируется, кто обязан начать писать поле, добавленное после заморозки. Устное
согласование проверить нечем; строка здесь переживает и ветку, и сессию.

| Поле | Кто обязан заполнять | Когда | Состояние |
|---|---|---|---|
| `AuditEvent.argvFromParams` | E2 собирает argv и знает, какие элементы пришли из параметров; E4 ассемблирует событие | стадия `build_argv` | **не сделано** — добавлено в E7, потребителей-производителей ещё нет |
| `ApprovalRequest.argvFromParams` | E5 собирает запрос подтверждения и переносит в него индексы из события стадии `build_argv` | стадия `approval` | **не сделано** — добавлено в E7, ветки E5 ещё нет |

Индексы во второй строке — не новое знание: они уже посчитаны на `build_argv`, и E5 обязан
их **перенести**, а не вычислить заново. Пересчёт по значениям разъедется там, где редакция
вырезала секрет, — ровно в том вызове, ради которого подтверждение и спрашивают.

**Проверку инварианта на стороне потребителя ставит E5, вместе с правилом `R41`.** В E7
нарушение деградирует в пропавшую подсветку: единственный потребитель идёт по `argv` и
спрашивает `includes(index)`, то есть индексом ничего не индексирует. В правиле выбора токена
цена другая — человек набирает не тот токен. Канонизация же с 2026-08-28 отвергает и
нефинитное число, и **дырку** в массиве: до этого дырка тихо уезжала на диск и давала другой
хэш при перечитывании, то есть опечатка производителя выглядела бы как подделка лога.

E6 править не нужно: `packages/core/src/audit/log.ts` принимает событие целиком, а его
проверка на границе чтения пропускает неизвестные лишние поля.

## Контрольные точки

| После | Проверяю |
|---|---|
| E0 | Три заглушки грузятся, схема валидирует манифест |
| Волна 1 | Каждая ветка зелёная изолированно, конфликтов по файлам нет |
| E4 | `run_tests` проходит 13 стадий end-to-end |
| E8 | Baseline `none` показывает ASR заметно выше seatbelt — иначе песочница бесполезна |
| E9 | Демо укладывается в 7 минут без запинок |

## Если время кончается

Резать в этом порядке: `container`-заглушку → E5 до «один раз / всегда» без TTL →
часть корпуса E8 (но **обязательно оставить S5 supply chain и baseline**).

Не резать: две линии обороны, S5, baseline-режим, честные границы.
Без них демо не доказывает тезис.
